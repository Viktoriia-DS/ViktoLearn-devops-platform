# Kubernetes Architecture

ViktoLearn runs on a local Kind Kubernetes cluster and uses Helm as the application deployment source of truth.

The application namespace is `viktolearn-helm`.

## Application Workloads

The platform contains three primary workloads:

- FastAPI application (`api`)
- PostgreSQL database (`postgres`)
- Redis cache (`redis`)

Each workload is deployed through the ViktoLearn Helm chart in `helm/viktolearn`.

## Helm

The Helm chart defines the Kubernetes application configuration, including Deployments, Services, persistent storage, security settings, resource controls, networking rules, monitoring integration, and Gateway API resources.

CI renders and validates the chart before an application image can be delivered.

The image tag stored in Helm values is an immutable Git commit SHA generated by the CI/CD pipeline.

## GitOps Reconciliation

Argo CD tracks the `main` branch and the `helm/viktolearn` directory.

Automated synchronization is configured with:

- pruning enabled;
- self-healing enabled.

This means Git represents the desired application state. Manual drift can be corrected by Argo CD reconciliation.

## Gateway API and Networking

External application routing is modeled with Kubernetes Gateway API resources.

The request path is:

```text
Client
  |
  v
MetalLB LoadBalancer address
  |
  v
Envoy Gateway
  |
  v
HTTPRoute
  |
  v
FastAPI Service
  |
  v
FastAPI Pod
```

The application hostname is `viktolearn.local`.

MetalLB supplies a LoadBalancer address inside the local Kind/Docker network. Envoy Gateway implements the Gateway API data plane.

Because Docker Desktop networking on macOS does not directly expose the MetalLB address to the host, Gateway routing was validated from inside the cluster.

## NetworkPolicy

NetworkPolicy resources restrict intended traffic between the API, PostgreSQL, Redis, Envoy Gateway, and monitoring components.

The main Kind cluster uses kindnet. kindnet accepts NetworkPolicy resources but does not enforce them.

Policy enforcement was therefore validated separately in a disposable Kind cluster using Calico.

## Workload Security

The application containers use Kubernetes security contexts including:

- non-root execution;
- explicit user and group IDs;
- read-only root filesystems;
- disabled privilege escalation;
- dropped Linux capabilities;
- RuntimeDefault seccomp profiles.

PostgreSQL uses a narrowly scoped initialization container to prepare fresh persistent volume ownership before the non-root database container starts.

## Resource Management

CPU and memory requests and limits are defined for application workloads.

A namespace ResourceQuota limits aggregate CPU, memory, pod count, persistent volume claims, and requested storage.

Readiness and health behavior are used to support workload availability and Kubernetes reconciliation.

## Kubernetes Validation

The CI pipeline validates the rendered Helm resources with multiple layers:

- Helm linting and rendering;
- custom rendered-manifest security validation;
- kube-linter;
- kube-score.

This catches configuration problems before the GitOps delivery stage.
